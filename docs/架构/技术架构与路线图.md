# 技术架构与路线图

## 总体架构 (分销/SaaS分站架构)

为了适应商业化运营与快速分销部署，项目采用「主站网关 + 独立业务分站」的解耦架构。这种模式能够保障核心资产安全，同时便于分销商（加盟站长）进行品牌贴牌（OEM）推广：

```text
终端消费者 (散客) ──> 扫码充值 / 创意画板 (React 前端)
                              │
                              ▼
                       [ 业务分站层 ]
                (Wails 桌面端 / Gin 网页端 - Go)
                   - 管理用户画布、本地资产、扫码支付
                              │
                              ▼ 携站长 API Key 调用
                       [ 核心网关层 ]
                     (12ZX-AI 主网关 - Go)
                   - 统一计费、通道调度、高并发熔断
                              │
                              ▼
                       [ 底层 AI 渠道 ]
               (可灵、即梦、Midjourney、OpenAI 等)
```

1. **核心网关层 (12ZX-AI)**：
   - 作为系统底座与计费中台，统一管理所有底层 AI 渠道（OpenAI, Midjourney, 可灵, 即梦等）的调度、限流降级与费率扣减。
   - 提供标准化的 API 接口，并向分站站长分发 API 令牌 (Token)。
2. **业务分站层 (Reveria Web & Client)**：
   - **后端**：使用 Go 语言开发。提供项目管理、画布持久化、资产本地化下载与缩略图生成、微信/支付宝/Stripe 支付收单。
   - **前端**：使用 React + TypeScript 开发。提供无限网格画布、生图/视频面板、历史资产管理等高颜值客户端。
   - **多端形态**：
   - **桌面端**：使用 **Wails 框架** 将 React 前端与本地素材缓存、导出和原生处理能力打包为客户端；项目、任务、账户及协作数据统一连接云端业务 API。
     - **网页端**：由 Web API 提供服务，部署在云端，面向广大付费散客用户提供在线服务。

## 推荐技术栈

### 桌面端与网页端分站

- **后端**：Go (Gin / Gorm / Wails) + Rust (底层原生图像处理引擎 DLL)
- **前端**：React / TypeScript / Vanilla CSS / Vite
- **外壳**：Wails（Go + 系统 WebView，与网页端共用 `packages/shared`）
- **数据库**：见下方「数据库定性」。生产主库为 PostgreSQL；Web 与桌面端都不直连数据库。

### 数据库定性

业务数据只属于 **Go API（业务分站）**，不属于网页端或桌面端。Web 与 PC 都是同一套云端 API 的客户端，看到的项目、积分、素材记录必须是同一份账本。

| 位置 | 引擎 | 用途 |
|------|------|------|
| 云端 / 正式环境的 API | **PostgreSQL** | 用户、工作区、项目、任务、积分、精修参数等全部业务数据 |
| 网页端 / 桌面端 | 不连接数据库 | 只调用远程 API；桌面端本机仅缓存图片文件、导出结果和原生处理产物 |
| 本机开发 API | SQLite（默认） | 开箱即用，不强制本机安装 PostgreSQL |
| 单元测试 | 内存 SQLite | 隔离、可重复 |
| 未来离线元数据（未立项） | 桌面端 SQLite | 仅在明确需要离线修图索引时引入，**不得**作为业务主库 |

约束：

1. **正式产品定 PostgreSQL。** 上线、多人协作、分销分站都必须把 API 切到 PG（`DATABASE_TYPE=postgres` + `DATABASE_URL`）。
2. **客户端不直连数据库。** 桌面端不得内嵌业务库，也不得把 PG 账号下发到客户电脑。
3. **SQLite 不是 PC 形态的主库。** 它只用于本机开发、测试，以及将来可能的离线元数据。
4. **不要做两套业务库。** 禁止「网页走 PG、电脑走本机 SQLite」这种分裂账本。

代码已同时支持两种引擎（`services/api/database/database.go`）。当前开发默认仍是 SQLite，属于便利配置，不是产品选型。

### AI 接入与网关 (上游)

- **12ZX-AI**：指定调用此项目作为多模型网关、智能路由与站长计费中台。
- **适配能力**：原生级支持 OpenAI 格式、Gemini 格式，深度支持可灵 (`kling_adapter.go`)、即梦 (`jimeng_adapter.go`) 等视频与多模态模型中转。

### 计费与观测

- **双重计费模式**：
  - **分站本地计费**：分站有独立的点数系统（包月套餐、充值次数等），供散客消费。
  - **主站网关计费**：分站每次生成调用，会通过站长在主站 the API 令牌，在你的 12ZX-AI 中扣减站长的批发额度。
  - **欠费熔断机制**：站长在主站欠费时，网关返回 402，分站自动拦截散客请求并熔断，倒逼站长去主站充值。

## 为什么不直接使用 12ZX-AI 的控制台作为唯一产品

12ZX-AI 的核心定位是“API网关与中台”，它的工作台界面面向的是**系统管理员（Owner）**或**API客户（开发者）**，用于渠道管理、费率配置与调用监控。
如果将散客直接引入该界面：
1. **安全风险高**：易暴露底层真实渠道及分发令牌。
2. **体验不专业**：界面充斥技术名词（API Key、IP白名单、重定向等），不符合普通消费者习惯。
3. **功能不匹配**：消费者需要的是富交互的画板、生成历史管理等生产力工具，这些应该由业务分站承载。

## 自研和借力边界

应该自研（在业务分站中实现）：

- 微信/支付宝/Stripe 在线支付收单
- 用户管理与独立分站账本
- 项目管理、素材资产库（支持缩略图与本地持久化）
- 基于 Wails & React 的无限画布
- 分站站长后台（可填入主站 API URL 与 API Key）

不建议一开始自研（在 12ZX-AI 中复用）：

- 基础大模型适配层
- 渠道健康检测与故障熔断
- 跨模型协议的高保真双向转换
- 各大视频模型（可灵、即梦等）的底层任务轮询及计费扣费队列
